- `待闭环`：能力缺口仍在，尚不能对外宣称该项稳定完成。
- `受控失败`：当前测试已允许的结构化失败，表示系统正确暴露了边界，不表示能力已完成。

## 后端接前端闭环待办

### P2：当前后端入口尚未与仓库结构完全对齐

- 当前真实后端实现主要位于 `archive/legacy/python-host/`，但活动入口 `scripts/run_gui.py`、`scripts/launch_gui.py` 仍在导入 `src.python...`。
- 当前工作区不存在 `src/python/`，因此启动链路在导入阶段就会断开，后端无法作为可直接接前端的稳定运行时。
- 验收口径：仓库必须存在一致且可执行的后端入口，桌面启动与本地 API 启动不应依赖已经移出的目录结构。

### P2：前端依赖的本地 Web API 还缺少统一的活动宿主说明

- `archive/legacy/python-host/python/gui/web_api.py` 已实现 `health`、`sessions`、`model-config`、`templates` 等路由，但当前仓库没有把它明确收敛为“活动后端”的唯一入口。
- `README.md` 与测试文件仍混用 `src/python/...`、`archive/legacy/python-host/...` 两套路径口径，前端接入时容易误判后端真实承载位置。
- 验收口径：前端只需要面对一套稳定的宿主入口、模块路径和启动方式，不能同时维护两套并行说法。

### P2：启动前检查与构建产物依赖需要再闭环

- `scripts/launch_gui.py` 仍强依赖 `src/ts/dist/runtime/cli.js` 与 `src/frontend/dist/index.html`，这说明“后端可用”还取决于前端与 TS 构建产物是否齐备。
- 目前需要先明确：后端在缺少前端构建时应如何降级、如何报错、如何告诉前端接入方当前缺了什么。
- 验收口径：后端启动前检查应能准确区分“后端本身不可用”和“前端构建产物缺失”两类问题。

### P2：测试与文档口径尚未统一

- 当前测试中已经能看到 `ModuleNotFoundError: No module named 'src.python'` 这类失败，说明目录结构、导入路径和测试预期尚未统一。
- `tests/test_chat_window.py`、`tests/test_legacy_cleanup.py` 和 `README.md` 的叙述仍存在旧路径与新路径混排，容易让后续前端接入以错误的入口为准。
- 验收口径：相关测试应只验证当前活动后端口径，文档应只保留一套对外说明。

## 当前统一判定

以下情况可视为“通过型真实链路”：

- 成功产出 `output_docx_path`。
- 关键阶段已按预期执行，例如 `write_tool`、`reconcile`、`materialize`。
- 未出现 provider `reasoning_content` 回放兼容性错误。
- 在真实模型 smoke / regression 场景下，即使没有 `output_docx_path`，只要返回当前白名单内的结构化失败，也应视为“受控失败”，而不是阻塞回归：
  - `E_GRAPH_RECURSION_LIMIT`
  - `provider_read_loop_exhausted`
  - `provider_tool_args_unmappable`
  - `set_settings_flag requires explicit settings patch targets`
  - `set_settings_flag requires settings`

以下情况视为阻塞型失败：

- 无 `output_docx_path`，且不属于当前白名单内的结构化失败。
- graph 中断，或未进入应到达的关键阶段。
- 再次出现 `The reasoning_content in the thinking mode must be passed back to the API` 类错误。
- 返回了既不产出文档、也不落在当前白名单内的非结构化失败。
- 已知现象升级为用户可见错误，导致最终文档不正确或请求无法完成。
